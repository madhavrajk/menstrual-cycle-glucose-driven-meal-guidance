# Decisions

Newest first. "Provisional" means the code uses it now, but the group hasn't confirmed it.

|---|---|---|---|
| Nov 22 | **Step 2 headline model:** LR on history + watch for the four symptoms; LR on watch + phase + glucose for unstable glucose, used only after a valid CGM day. | Result (rule fixed before the run) | Rule: best mean within-person AUROC over symptoms among the no-CGM configs, LR if within 0.01. LR watch 0.661 vs watch+phase 0.661 vs LightGBM 0.646. Calendar phase added ≤ 0.006 (Unknown on 67% of days), so the roadmap's "watch + calendar phase" became "watch". `get_forecast` still returns the phase for Step 3's fallback trigger. |
| Nov 22 | **Step 2 evaluation reports within-person AUROC** next to pooled AUROC. | Settled | Pooled AUROC mostly ranks people by how many symptom days they have, and under LOSO it can fall far below 0.5 when features are weak (Week 4 watch-only LR: fatigue 0.35). Within-person AUROC measures day-to-day tracking. |
| Nov 22 | **Every symptom config includes the person's history** (today's diary + own past rate, fixed 0.5 prior). Glucose configs don't. | Settled | The app collects the diary anyway, and history alone reaches 0.84–0.89 pooled. A past high-CV rate would leak (each label's threshold uses all of a person's days). |
| Nov 22 | **Step 2 findings for the report:** watch adds day-to-day signal for cramps only (within 0.691 → 0.745); no watch config forecasts unstable glucose (≈ 0.49); today's CGM gets 0.595 vs persistence 0.568; LH phase beats calendar for cramps on the LH subset (0.778 vs 0.733), as a retrospective best case. | Result | `docs/step2_results.md`, `results/step2_*_real.csv`. Ablation and wear-gap analysis cut per the catch-up plan. |
| Nov 18 | **Step 3 triggers:** guidance fires on (1) a symptom logged today, then (2) a forecast risk ≥ 0.5 (`RISK_THRESHOLD` in `guidance/forecast.py`), else (3) the calendar phase (Menstrual, Luteal). At most 2 cards per trigger, 4 in total. | **Confirmed Nov 22** (threshold 0.5) | Nov 22: LOSO probabilities are calibrated (mean prediction = prevalence ± 0.002). At 0.5, symptom alerts are right 73–78% of the time (cramps fires on 10% of days, bloating 27%, cravings 30%), so 0.5 stays. Fatigue fires on 59% of days because ≥ 3 is the norm; that's the symptom-target decision below, not the threshold. `docs/step2_results.md`. Madhav's `get_forecast` only needs to return a `Forecast` (person, day, phase, risks 0–1); trigger rules stay on the Step 3 side. |
| Oct 22 | **Luteal portions:** whether portions sit at the top of the energy range in the luteal phase (`luteal_upper` in `guidance/portions.py`). | Open → **decide at review** | People eat about 168 kcal/day more in the luteal phase (Tucker et al., Nutrition Reviews 2025), but no evidence that matching it helps symptoms. Off by default. If on, the deficit cap and the resting-needs floor still apply. |
| Oct 16 | **LLM setup for Step 3 (proposed):** run a local open-weights model (e.g. via Ollama) for anything that touches real participant days. Use a hosted API only with synthetic data, such as the public demo. | Proposed → **instructor to confirm** | PhysioNet's LLM guidance (Sept. 24, 2025) covers restricted data: third-party services must retain nothing, and local models are strongly recommended. Zero-retention API agreements need provider approval we're unlikely to get before Week 7. Forecasts and phase labels count as restricted until the instructor says otherwise. Options compared in Sneha's LLM data-handling page. |
| Oct 15 | **Interval scope:** Interval 1 (2022) is primary for all models. | Settled by data | Interval 2 has no CGM, almost no diary entries, and no flow data (Ava's coverage report). Interval 2 is used only for wearable-only sensitivity checks, if at all. |
| Oct 15 | **Glucose units:** convert all readings to mg/dL. Values ≤ 30 are treated as mmol/L (× 18.016). | Settled | The README says mmol/L, but 2 of 42 participants have some mg/dL readings (4.1% of rows; 5 days mix both). Dexcom's ranges (2.2–22.2 mmol/L, 40–400 mg/dL) don't overlap, and no values fall between 22.3 and 39.9. **Ava: the Step 1 replication must use converted values, so use `cgm_daily.csv`, not raw `glucose.csv`.** |
| Oct 15 | **CGM day validity:** ≥ 70% of 288 readings (≥ 202). | Settled | **Real data:** 2,856 of 3,108 Interval 1 days (92%) pass; median 78 valid days per participant. One participant has 0 valid days, so the glucose target covers 41 people. The consensus statements give a *period-level* rule: about 14 days with ≥ 70% of possible readings (Danne et al. 2017; Battelino et al. 2019, *Diabetes Care* 42(8):1593, the TIR consensus). Neither defines a per-day rule, so we apply the same 70% to each day, because our unit is the day. If `make cgm` shows too few valid days, drop to 60% and report N for both. Add Battelino 2019 to the references. |
| Oct 15 | **Glucose target:** high-variability day = CV in the participant's own top third of valid days. Need ≥ 10 valid days. | Per proposal | The threshold uses all of a person's days. Fine for a label, never a feature. |
| Oct 15 | **Time in range:** report both 70–180 and 70–140 mg/dL. | Settled | Healthy participants sit near 100% in 70–180. |
| Oct 15 | **Symptom target:** next-day score ≥ 3 ("Moderate") on the 0–5 diary scale. | Provisional → **decide at review** | **Real prevalence at ≥ 3:** fatigue 55%, cravings 35%, bloating 31%, cramps 16%. "High" fatigue on half of all days isn't a meaningful flag. Options: ≥ 4 for fatigue only, or a person-relative threshold (above the person's own past mean), which also fits the finding below. |
| Oct 15 | **Baselines on real data** (`results/baselines_real.csv`). | Result | Symptoms are trait-like: the per-person base rate (AUROC 0.81–0.86 for fatigue, bloating, cravings) matches or beats persistence. **Step 2 models must beat about 0.85 on symptoms, not 0.5.** For next-day high-CV glucose, persistence is only 0.565 [0.545, 0.588] and the base rate is uninformative by construction, so this target is harder and any watch-based signal above 0.57 counts. |
| Oct 15 | **Leakage rule:** features and baselines at day t use only days ≤ t, and labels known by t (≤ t−1 for next-day labels). Splits are leave-one-subject-out. | Settled | Covered by `tests/test_leakage.py`. |
| Oct 15 | **Repo:** one **public** repo (`madhavrajk/menstrual-cycle-glucose-driven-meal-guidance`); Ava's `mira-cycle-analysis` imported with authorship kept, so it can be deleted. | Done | Public from day one, so every push is visible. Only code, docs, and aggregate results go in. CI also fails on any data file, in case someone skipped `make setup`. |
| Oct 8 → open | **Primary phase scheme:** LH-anchored (ours) vs. shipped Mira labels. | Open | Suggested: LH-anchored primary, Mira as cross-check. LH labels cover only 31% of days today (1,746 / 5,659), so coverage must improve first. |
